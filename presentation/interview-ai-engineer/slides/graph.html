A graph because the branches are real, not because graphs are fashionable

Conditional edges that save money

Three branches short-circuit the expensive path:

  • Every group was a duplicate → skip extract and persist entirely
  • Quota exhausted mid-pass → leave messages unparsed for the next run rather than writing "no events found"
  • Approval disabled → skip screening, which is itself an LLM and embedding spend

Screening only earns its calls when a human will actually be asked to approve the result.

What I deliberately did not use

FeatureWhy not
interrupt()Resume re-runs the node from the top, and approval has already written to SQLite — every card would go out twice. The PENDING row is the durable interrupt, and it survives a restart.
checkpointerUnparsed rows are already the durable work queue. A crash is recovered by the next pass reading the same rows.
tool loopThe pipeline is fixed. A loop would add non-determinism to a path that writes to a family's calendar.

Eight nodes · three conditional edges · no checkpointer, on purpose

This is the slide I would want to be asked about. The left side is ordinary: conditional edges that let the graph skip work. The interesting number is the third one — screening costs an LLM call and an embedding call per event, so it only runs when approval is actually on and there is something to approve. The right side matters more. Every one of those three is a LangGraph feature I read about, wanted, and rejected with a reason. interrupt() is the big one. Human-in-the-loop is textbook LangGraph. But resume re-runs the node from the top, and by then requestApproval has already written to SQLite and sent a WhatsApp card. A resume would send every card a second time. So the PENDING database row is the interrupt — and unlike an in-memory thread, it survives the process dying. If you take one thing from this deck: I can tell you why I did not use a framework feature, in terms of what would have broken.
