Embedding systems

The same retrieval problem, re-engineered for a 12× tighter budget

On the desktop

Gemini gemini-embedding-001, 3072 dimensions, cosine over a bounded candidate pool — 30-day window, 1000 rows, served by a composite index. Threshold 0.92, user-tunable.

Vectors stored as JSON. Fine on a laptop.

Then I measured it

The live database was 40 MB holding 100 messages. A 3072-dim vector as JSON text is ~39 KB per row — so one dedup pass parses roughly 39 MB of JSON.

Tolerable on a laptop. Not on a phone.

On the phone

Int8 symmetric quantisation, L2-normalised on encode so similarity is a plain dot product. 3,076 bytes per vector, compared straight out of the row with no allocation.

768 dimensions via Matryoshka truncation — 4× less again.

0.001

A test pins quantised similarity to within 0.001 of exact cosine, so a 12.7× size win cannot move a score across the 0.92 threshold. Mismatched dimensionality returns null rather than a score — a changed model can never silently compare across vector spaces.

Bounded candidate pool · O(n) cosine in-process · no ANN index, and I can tell you when that stops being fine

Three panels: the same retrieval problem at two very different budgets. The middle one is the one I would lead with in a technical conversation, because it is the habit rather than the trick: I measured before I redesigned. Forty megabytes for a hundred messages, and when I looked, it was almost all embedding JSON and base64 images. The right panel is the fix — int8 quantisation, normalise on encode so cosine becomes a dot product, and read it straight out of the row without allocating an array. The number at the bottom is the part that makes it safe. A size optimisation on a similarity threshold is a correctness change unless you prove it is not. So there is a test asserting the quantised score stays within a thousandth of exact cosine — comfortably tighter than the gap between the threshold and the scores actually observed. If asked about scale honestly: this is a bounded linear scan, not an ANN index. At a thousand candidates in-process that is the right call. I know where the line is — and in a bank I would be reaching for pgvector or OpenSearch, with the same threshold-validation test around it.
