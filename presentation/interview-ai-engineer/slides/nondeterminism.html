Non-determinism at scale

The same flyer reaches three class groups. Five mechanisms stop it becoming three events.

Mechanism What it catches Cost If it fails
L1 · hash A byte-identical forward Nothing — no network Falls through to L1 embedding
L1 · embedding A forward that gained "FYI" One embedding call Open — treated as fresh, goes to the model
Collapse One gathering described at several times Nothing — deterministic Cannot fail; that is why it exists
L2 · exact Title + date + time + child already stored One indexed query Falls through to L3
L3 · judge "Same gathering, different framing" One LLM call per sibling Open — duplicate reaches the approval queue
L4 · calendar An entry a parent added by hand, ±60 min Embeddings over candidates Open — duplicate reaches the queue

Cheapest first, and every layer fails open on purpose. A duplicate card the user dismisses is an annoyance; an event silently suppressed by a transient model failure is a missed school trip. The deterministic collapse exists precisely because the layer above it can fail open.

L1–L2 prevent a row · L3–L4 reject one already written, so the suppression is auditable

This is the heart of it, and the slide I would spend the most time on. Read the Cost column top to bottom: the order is deliberate. SHA-256 costs nothing, so it goes first and catches the most common case — someone forwarding the identical flyer. Embeddings cost one call. The LLM judge costs a call per sibling, so it is last. Now the "If it fails" column, which is the part I actually care about. Every one of these fails open. That was a decision, not an accident. I wrote it down in the code comments so the next person does not "fix" it. And the asymmetry is the reason: a duplicate the user has to dismiss is mildly annoying. An event that was silently dropped because an embedding call timed out is a missed school trip, with nothing in the UI to show it ever existed. Those are not equal, so the failure mode is not symmetric either. Last point, bottom of the slide: layers 3 and 4 run after the row is written and mark it REJECTED rather than preventing the insert. That means a suppressed duplicate is a row you can audit, not an absence you cannot. In a bank that distinction is the whole game.
