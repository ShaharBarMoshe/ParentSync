LLM-as-a-judge · evaluation

A model judging a model, with a deterministic floor underneath it

The judge

Layer 3 is a dedicated port — IDuplicateJudge — asked one question: do these two events describe the same gathering? It runs against same-slot and same-day siblings for that child.

It is a judge, so it is treated as fallible: one call per sibling, a hard fail-open, and a deterministic collapse running before it that catches the common case without a model at all.

Every firing increments a counter, so the judge's rate is observable rather than assumed.

Structured output is a contract, and it bites

Gemini rejects parts of JSON Schema at call time, not build time: no nullable, no unions, no additionalProperties. A schema that is valid and type-checks can still be refused in production.

So a test runs the real zod → JSON-Schema conversion, not a mock of it. Mocking the conversion would hide exactly the failure the test is for.

Every field is a plain string — including confidence — because the subset has no way to say "integer or absent", and a required integer makes the model invent a number it has no view on.

Eval-first: error analysis before metrics · retrieval and generation measured separately

Two halves, both about trusting a model only as far as you have evidence. The judge is a real LLM-as-a-judge in production, not a benchmark exercise. What I would emphasise is that I treated it as fallible from the start: it fails open, it is the most expensive layer so it runs last, and there is a deterministic collapse in front of it that handles the common case — one gathering described at several times — without any model involvement. The judge only sees the genuinely ambiguous pairs. And it is instrumented. I can tell you how often it fires, because it increments a counter when it does. The right half is the one that surprises people. Gemini's structured-output path rejects parts of JSON Schema at call time. You can write a schema that is valid JSON Schema, passes type-check, passes every mocked unit test, and is refused by the API in production. So the test exercises the real conversion. Mocking it would hide the one failure the test exists to catch. That is the eval instinct generally: test the thing that actually fails, not the thing that is easy to assert.
