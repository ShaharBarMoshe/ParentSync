Load, limits and failure

Not every 429 means the same thing — and treating them alike cost hours of guaranteed-failing traffic

One place for the policy

Every model call goes through one runner, in one order: shared rate limiter → retry ladder → tracing → invoke. One slot per call, so a burst cannot starve extraction.

Generic framework retry could not express the rule that mattered, so the policy is explicit and tested.

The rule that mattered

Google returns 429 both for a per-minute rate limit and for a depleted account. Only the first clears on its own.

  • Non-429 4xx → never retried
  • Depleted account → fails on the first attempt, aborts the pass
  • Everything else → exponential backoff

What it cost before

One dead account meant 8 retries per message plus a per-message fallback — hours of traffic that could not succeed.

Worse, the swallowed error marked those messages parsed with no events, losing them permanently. Now they stay unparsed for the next pass.

Coalescing, not queuing

Two passes started 90 ms apart both read the unparsed rows before either marked anything, and both created events — near-identical duplicates no dedup layer catches, because they are built concurrently from the same input. A second caller now joins the in-flight pass instead of starting a rival one.

Backpressure at the edge

On mobile, a busy group delivers a dozen notifications in seconds. Work is enqueued with a 45-second coalesce window under KEEP, not REPLACE — REPLACE would push the run further out on every new message and let a chatty group starve the pass indefinitely.

Transactional writes · a rollback leaves messages unparsed, so the next pass retries them

This is the slide for the "high load, traffic spikes, failure scenarios" line in the job description. The centre column is the real content. Google returns 429 for two completely different things: you are going too fast, and you have no money left. One clears by waiting; the other never does. Retrying the second is pure waste, and worse, it burns your retry budget on a wall. The right column is what that actually cost before I separated them: eight retries per message plus a per-message fallback, so a single expired key produced hours of traffic that was guaranteed to fail. And the swallowed error marked those messages as parsed-with-no-events, which quietly lost them for good. That second part is the bug that mattered — the retries were just money. Bottom left is a concurrency bug worth naming because no dedup layer could have caught it. Two passes ninety milliseconds apart, both reading the same unparsed rows before either marked anything. Built concurrently from identical input, so they are not duplicates by any content test — they are a locking problem. The fix is that a second caller joins the running pass. If asked what I would change in a bank: this is in-process coalescing because it is a single-process app. The same shape in your environment is a queue with a visibility timeout and a DLQ — the policy is identical, the mechanism is managed.
