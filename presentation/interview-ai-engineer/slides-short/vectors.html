39 KB per vector → 3,076 bytes. I measured before I redesigned.

And proved the 12.7× win stays within 0.001 of exact cosine.

Two numbers, two habits. The measurement first. The live database was forty megabytes holding one hundred messages. When I looked, almost all of it was embedding JSON — a 3072-dimension vector stored as JSON text is about thirty-nine kilobytes, and a dedup pass reads up to a thousand candidates. So one check parses roughly thirty-nine megabytes of JSON. Fine on a laptop, not on a phone. The fix: int8 symmetric quantisation, L2-normalised on encode so cosine becomes a plain dot product, read straight out of the database row without allocating an array. Three thousand and seventy-six bytes. Now the second number, which is the part that makes it safe. A size optimisation sitting on a similarity threshold is a correctness change unless you prove otherwise. So there is a test asserting the quantised score stays within one thousandth of exact cosine — comfortably tighter than the gap between the 0.92 threshold and the scores actually observed. Mismatched dimensionality returns null rather than a score, so a changed embedding model can never silently compare across vector spaces. Honest scale note if asked: this is a bounded linear scan over a thousand candidates in-process, not an ANN index. Right call at this size. In your environment I would reach for pgvector or OpenSearch — with the same threshold-validation test wrapped around it.
