Incident

It read its own output and fed itself. One message became 100 rows.

Nothing crashed. The first symptom would have been the bill.

10 / 13

I volunteer this one. It is the most transferable thing I have. The setup is almost funny. The mobile client warns you when messages are waiting but no API key is set. That warning is a notification. The client reads notifications. So it read its own warning, stored it as a message, which raised the count of waiting messages, which re-posted the warning. One real message became a hundred rows. Here is why it matters rather than being a joke: nothing crashed. No exception, no failing test, no alert — the system looked healthy. With an API key configured, every one of those rows would have been a paid model call on the app's own text, and the first thing anyone would have noticed is the invoice. I found it by dumping actual database state on an emulator instead of trusting that a green test run meant a healthy system. That instinct is the thing I would bring. The fix is a guard that cannot be turned off by configuration, checked before the source test, with a test asserting it cannot be configured away. A watch list is a user preference; "do not consume your own output" is an invariant. The generalisation: any agentic system that both emits and consumes needs an explicit identity boundary, or it will eventually consume itself — quietly, and in a metered system, expensively.
