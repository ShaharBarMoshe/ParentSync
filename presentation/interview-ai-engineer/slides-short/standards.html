Standards the build enforces, not standards a wiki describes.

Import the AI framework outside its two layers and the build fails.

11 / 13

This is the internal-tooling argument in one line, and it is a line from the job description. There is a test that walks the source tree and fails the build if anything outside the adapter and graph layers imports the AI framework. The framework cannot leak into the domain because somebody forgot at review time. An executable standard beats a documented one. Three supporting facts if they want them. The end-to-end suite compiles and bundles both applications, because a mocked unit test cannot catch a missing import in a module it mocks. I had those timeouts set too tight at one point and the suite failed about half the time — which teaches everyone to ignore a red build, so I fixed the timeouts rather than living with it. There is a production smoke test: six steps that drive a real message end to end through the live system on every deploy and daily, and eight more that clean up after it — the calendar event, the rows, and the test message itself. A self-test that leaves artefacts behind is one you stop running. And tracing is framed as a data-egress decision rather than a debug flag: it is opt-in, and the documentation states what leaves the machine when you turn it on. In a bank that framing matters more than the tracing.
