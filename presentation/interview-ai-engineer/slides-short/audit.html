Layers 3 and 4 run after the write, and mark it rejected.

This is the slide for a banking audience specifically. The first two dedup layers prevent a row from existing. The last two run after the insert and mark it REJECTED instead. That looks like a quirk and it is deliberate: when the system decides not to act, that decision is itself a record — with a status, and a counter that reconciles against the table. Compare it to a pipeline where a suppressed item simply never appears. You cannot audit an absence. You cannot answer "why didn't this show up" six weeks later. Three more controls in the same family, if there is appetite: Nothing reaches the calendar unapproved, and the durable record is a database row rather than a UI state — so dismissing a notification decides nothing and a restart loses nothing. OAuth 2.0 with PKCE, CSRF state, refresh tokens encrypted at rest, and a separate client per purpose — that last one came from a real race that only showed up against the actual Google library, which is why the test uses the real one instead of a mock. And an alert never travels over the channel that is broken. WhatsApp failures are reported by email; Google failures over WhatsApp. Obvious written down. Not obvious when the only alerting path was the thing that had just died.
